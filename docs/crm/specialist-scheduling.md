# Специалист, индивидуальный график и отсутствие

Контракт владельца от 2026-09-21, V1-F06 / V1-W02. Реализация и проверки
отслеживаются в [PRIMARY-SESSION](../testing/task-state/PRIMARY-SESSION.md).
Этот документ описывает согласованное поведение; сам по себе не доказывает готовность.

## Специалист и время приёма

- Специалист — существующий `Resource` типа `staff`, принадлежащий Business.
  CRM-аккаунт (`linked_user`) необязателен. Создание специалиста не создаёт логин,
  приглашение, членство или отдельное правило оплаты.
- Недельный график — семь индивидуальных `WorkingHours`. В интерфейсе его
  проверяют при создании специалиста; карточка и неделя сохраняются атомарно.
  API без переданной недели копирует текущие часы бизнеса; отсутствующие дни
  становятся выходными. Дальнейшее изменение бизнес-графика не переписывает копию.
- Для прежних ресурсов сохраняется существующее наследование бизнес-графика
  на дни без собственной строки. Массовой миграции или выдуманного графика нет.
- `ScheduleException` заменяет расписание конкретного ресурса на конкретную
  дату в часовом поясе бизнеса: выходной либо другой интервал работы. Удаление
  исключения возвращает недельное правило. Один рабочий интервал в день;
  несколько смен и перерывы внутри дня не входят в эту реализацию.
- Календарь специалиста — существующий календарь с фильтром по его Resource.
  Не создавать независимую копию записей или второй календарный движок.
- Новая запись и перенос требуют активного специалиста того же Business.
  Комната, кресло или оборудование не заменяют специалиста. Проверяются график,
  исключение на дату, длительность услуги и пересечение записей.
- Legacy записи без специалиста сохраняются, доступны история и lifecycle.
  Для их переноса нужно явно выбрать активного специалиста; автоматического
  назначения врача по имени, ответственному менеджеру или владельцу нет.
- Отключение CRM-аккаунта/членства лишает доступа в CRM по существующим правилам,
  но не отключает независимую карточку специалиста. `Resource.is_active=false`
  запрещает новые записи/переносы к нему; историю и назначенные визиты не удаляет.
- Имена не являются уникальным идентификатором. Для уже связанного CRM-аккаунта
  использовать существующего специалиста, а не создавать второй staff Resource.
- Специалист и расписание управляются через `settings:update`; работа с записями
  сохраняет `appointments:update` и существующий OWN/TEAM/BUSINESS scope.

## Форс-мажор на выбранную дату — текущая реализация

1. Управляющий открывает индивидуальный график, выбирает дату и отмечает отсутствие
   либо изменённое время. Это состояние расписания, не блокировка логина.
2. После сохранения открывается окно разбора записей выбранного дня. В нём весь
   доступный пользователю список ещё активных записей этого специалиста, количество
   записей и уникальных клиентов; завершённые/отменённые визиты не требуют переноса.
   Список нельзя обрезать первой страницей API или скрывать за нулевым счётчиком
   при ошибке загрузки. Проверяются также записи заранее выбранной будущей даты.
3. Существующие записи не отменяются и не переносятся автоматически. Исключение
   сразу блокирует новые неподходящие бронирования. При частичном изменении смены
   показываются все активные записи дня, чтобы управляющий мог проверить ситуацию.
4. По записи можно выбрать другого свободного специалиста на то же время, другую
   дату/время либо отменить с причиной. Тот же сервис повторно проверяет доступность
   в момент сохранения; устаревший свободный слот не разрешает двойную запись.
5. Перенесённые к другому врачу/на другую дату и отменённые записи исчезают из
   оставшегося списка. Замена сохраняет ту же запись и историю прежнего/нового
   специалиста, времени и причины. Повторно открыть список можно из графика.
6. Администратор завершает разбор вручную. Закрытие окна не означает уведомления
   клиента или его согласия. Новая рассылка в этом пакете не запускается.

Связанные заявки и клиенты остаются доступны через существующую запись/карточку.
Без CRM-аккаунта у специалиста нет автоматически выводимого владельца Tasks или
Leads. Нельзя объявлять все сущности менеджера отсутствующими только потому, что
его аккаунт связан со специалистом. Новая привязка исполнения других сущностей
к Resource потребует отдельного согласованного контракта.

## Уведомление клиентов — желаемый следующий шаг, НЕ реализовано

Владелец попросил задокументировать рассылку; подключение провайдеров и отправка
сообщений сейчас не разрешены. Переиспользовать существующие conversation,
notification delivery, templates, очередь и provider adapters.

| Ситуация | Решение управляющего | Сообщение клиенту |
| --- | --- | --- |
| Другой специалист свободен в то же время | Назначить замену, проверить сообщение | Кто принимает и когда; запрос подтверждения, если он нужен |
| Нужна другая дата | Сначала предложить вариант; после согласия изменить запись | Предложение времени отдельно от подтверждения уже сохранённого переноса |
| Решение пока не найдено | Оставить в работе и назначить контакт с клиентом | Предупреждение о невозможности приёма и обещание согласовать время |
| Клиент отказался / замены нет | Отменить с причиной | Подтверждение отмены, понятный способ связаться с администратором |

Порядок работы:

1. Окно показывает приоритет по ближайшему времени приёма, количество оставшихся
   записей и клиентов. Обработка изменения записи и контакт с клиентом — разные
   состояния; перенос не должен убирать клиента из очереди неотправленных уведомлений.
2. Управляющий выбирает записи, проверяет конкретное решение и предпросмотр текста
   для каждого получателя. Массовая отправка требует явного действия управляющего;
   флаг отсутствия сам по себе не отправляет сообщения и не меняет дату визита.
3. Канал выбирается по существующей связанной переписке и доступному контакту:
   WhatsApp, Instagram, Telegram при работающем подключении и разрешённой возможности
   отправки. Один только `source` заявки не доказывает наличие адресата или доступность
   канала. Не отправлять один текст сразу во все каналы и не подменять адресата.
4. Без доступного канала показать «связаться вручную» с имеющимся контактом. Для
   близкого визита оператор видит, кому нужно позвонить, не ожидая фонового retry.
5. Состояния доставки: подготовлено → очередь → отправлено → доставлено, если
   провайдер это подтверждает; отдельно ошибка/нужен ручной контакт. Прочтение,
   подтверждение клиента и фактический перенос — отдельные состояния.
6. Повторный запуск не дублирует отправку: ключ включает Business, запись, версию
   изменения, назначение сообщения и канал. При следующем переносе устаревшее
   неотправленное подтверждение отменяется. Проверять запись повторно перед отправкой.
7. Несколько визитов одного клиента показывать вместе; агрегировать уведомление
   только при одинаковом адресате, согласованном канале и непротиворечивом решении.
8. После ответа клиента менеджер подтверждает новую запись либо выбирает иной
   вариант. AI может подготовить текст/варианты, но не фиксирует перенос за сотрудника.
9. Audit связывает отсутствие, исходную запись, действие управляющего и delivery.
   Клиентскому тексту не нужны личные причины отсутствия врача или внутренние заметки.
   Не объявлять всех уведомлёнными по одному успешному ответу HTTP от провайдера.

Приёмка будущей реализации: повторная отправка без дублей, сбой/недоступный канал,
несколько записей одного клиента, изменение решения во время очереди, поздний ответ,
ошибка доставки и ручной контакт, tenant/role denial, неизменность записи до решения
управляющего, сохранение работоспособности обычной CRM без AI/канала.

## Кресла — отложено владельцем

Для четырёх врачей и двух кресел в будущем запись должна занимать врача и рабочее
место одновременно. Постоянная связь «один врач — одно кресло» не обязательна:
назначение делается на смену/запись; допустимые места и место по умолчанию могут
помогать выбору. Нужна проверка пересечения по обоим ресурсам. Сейчас вместимость
кресел системой не проверяется; управляющий учитывает её вручную. Существующие
non-staff Resource не удаляются, новая модель бронирования кресел не добавляется.
