## 2. Какие CRM-практики адаптируем

Это выбор механик, а не копирование схемы данных или полномочий чужой CRM. Официальные описания просмотрены 2026-09-16; конкурентные продукты в этом этапе локально не разворачивались.

| Источник | Полезная механика | Адаптация для Zani — ПРЕДЛОЖЕНИЕ |
| --- | --- | --- |
| [Frappe CRM: Deal](https://docs.frappe.io/crm/deal) | Сделка представляет квалифицированную возможность; при преобразовании заявки сохраняется коммуникационная история | Сохранять происхождение и доступную историю, но не заставлять сервисный бизнес создавать сделку для каждого визита |
| [EspoCRM: Sales management](https://docs.espocrm.com/user-guide/sales-management/) | Несколько способов появления заявки; преобразованная заявка остаётся доступной вместе со связями | Не удалять источник после создания результата. В Zani клиент уже обязателен для Lead, поэтому отдельную конвертацию Lead → Client не возвращать |
| [EspoCRM: Emails](https://docs.espocrm.com/user-guide/emails/) | Из обращения можно создать задачу либо заявку; видимая задача помогает распределять ответственность | У обращения допустим результат «ответили и закрыли», «передали сотруднику» или «создали работу», а не всегда продажа |
| [Twenty: Workflow triggers](https://docs.twenty.com/user-guide/workflows/capabilities/workflow-triggers) | Момент создания записи и момент заполнения её полей могут различаться | Для Zani проверять полные prerequisites перед действием и повторно перед отложенным выполнением; не запускать цепочку по незавершённой форме |

Не добавляем ради сходства с конкурентами Account/Organization, складской ERP, счета-фактуры, универсальный BPM или вторую систему ролей.

## 3. Смысл сущностей и допустимые результаты

| Сущность | За что отвечает | Чем не является |
| --- | --- | --- |
| Client | Идентичность и история отношений с человеком/контактом | Не отдельное обращение, не факт покупки и не учётная запись сотрудника |
| Lead | Конкретная потребность/заявка клиента | Не сам клиент и не обязательный предшественник любой записи |
| Deal | Коммерческая возможность в воронке | Не банковский платёж и не факт оказания услуги |
| Appointment | Согласованный интервал оказания услуги клиенту | Не задача сотрудника и не подтверждение оплаты |
| Task | Отдельное действие с исполнителем/сроком, когда они заданы | Не автоматический статус родительской заявки/сделки |
| Conversation / Message | Общение, ответственность, прочитанность и доставка | Не гарантированно квалифицированная заявка |
| Payment | Запись о вручную зафиксированном получении/возврате денег | Не платёж в пользу Zani, не подтверждение банка |
| Activity / Audit / BusinessEvent | Пользовательская история / контроль действий / нормализованное бизнес-событие | Не три независимые продажи и не три повода повторить одну операцию |

**ПРЕДЛОЖЕНИЕ:** результат процесса определяется целью конкретного обращения. Ответ на вопрос, выполненная задача, отказ с причиной, завершённый визит, выигранная/проигранная сделка — разные допустимые окончания. Завершение одной сущности не закрывает все связанные сущности.

Примеры равноправных путей: входящее → ответ → закрытие; ручной клиент → запись → визит; заявка → сделка → результат; самостоятельная задача → выполнение; форма → заявка → отказ; повторное обращение существующего клиента → новая работа. Ни один путь не требует искусственных промежуточных сущностей ради воронки.

| INV-07 | Отказ не оставляет частично созданных CRM-записей; повтор принятой команды не создаёт второе действие | КОНТРАКТ для имеющихся защищённых путей; ПРЕДЛОЖЕНИЕ как единая гарантия всех входов. Проверять границу транзакции по каждому действию |

| INV-09 | У сообщения, импорта, AI и автоматизации те же доменные запреты, что у ручной операции; служебный actor должен иметь явно ограниченный контекст выполнения | КОНТРАКТ; runtime parity проверяется отдельно |
| INV-10 | Сбой AI/провайдера не должен выдавать выдуманный успех. CRM остаётся работоспособной вручную в пределах доступных модулей | КОНТРАКТ; разделение transport/AI требует D-02 |

## 6. Жизненные циклы основных сущностей

### 6.1 Client: идентичность, повторное обращение, merge

**КОНТРАКТ:** создание → уточнение данных → использование в независимых обращениях; archive/restore отдельно. У Client нет статуса «продажа завершена». Существуют duplicate check, merge-dry-run и merge; перед merge нужен preview последствий. Источники: [API](../api/API_ACTION_CONTRACT.md), [identity](../../apps/clients/identity.py), [services](../../apps/clients/services.py).

**ПРЕДЛОЖЕНИЕ:** новый запрос того же клиента создаёт новую работу только при новом намерении, а не нового Client на каждое сообщение. Совпадение имени недостаточно для merge. Разные контакты с общим семейным телефоном не объединять автоматически. После merge остаются происхождение, audit и ссылки на сохранённую идентичность; задачи/платежи/визиты не исчезают и не удваиваются в метриках. Политику архива активного клиента согласовать в D-03.

### 6.2 Lead: потребность клиента

**КОД:** таблица переходов в [lead services](../../apps/leads/services.py), `ALLOWED_LEAD_STATUS_TRANSITIONS`:

| Из | Допустимые целевые состояния в helper |
| --- | --- |
| `new` | `contacted`, `in_progress`, `appointment_created`, `closed`, `lost` |
| `contacted` | `in_progress`, `appointment_created`, `closed`, `lost` |
| `in_progress` | `contacted`, `appointment_created`, `closed`, `lost` |
| `appointment_created` | `in_progress`, `closed`, `lost` |
| `closed`, `lost` | `new`, `contacted`, `in_progress` |

Это не разрешение выставлять любой статус через PATCH: конкретные public actions имеют свои guards. `lost` требует причины. `reopen_lead` выбирает previous status либо `in_progress`; взаимодействие с сохранённым previous status нужно проверять отдельно, не выводить гарантию из таблицы.

**КОД:** `create_deal_from_lead` возвращает уже связанную неархивную сделку, если она существует; иначе создаёт её и переводит заявку в работу. `mark_lead_appointment_created` — отдельная часть создания записи. Создание задачи не означает закрытие заявки.

**ПРЕДЛОЖЕНИЕ:** `closed` = обработка запроса закончена, `lost` = потребность не реализована с причиной; ни то ни другое не равно полученной оплате. «Есть запись» — операционный результат, а не терминальное состояние продажи. Одно входящее сообщение не должно само переводить заявку в `lost/closed`. Повторная самостоятельная потребность → новая заявка; продолжение прежней → существующая. D-05 задаёт правила повторного открытия/нового цикла.

### 6.3 Deal: коммерческий результат

**КОНТРАКТ + КОД:** `open` → разрешённые активные этапы своей Pipeline → `won` или `lost`; выход из терминального состояния — `reopen`. `lost` требует причины. Этап может требовать заполненных полей/custom fields и разрешённой роли. Stage, status, probability и terminal timestamps согласуются сервисом. Источники: [модели](../../apps/crm/models.py), [services](../../apps/crm/services.py), [serializers](../../apps/crm/serializers.py).

**КОД:** отсутствие записи `StageTransition` в `validate_stage_requirements` само по себе не запрещает переход. Наличие этой модели не означает strict allowlist графа переходов. Политику фиксирует D-08.

**ПРЕДЛОЖЕНИЕ:** `won` означает подтверждённый коммерческий успех, не автоматическую оплату и не завершённый визит. Выигрыш/проигрыш не отменяет связанные открытые задачи без явного действия. Показать их перед закрытием, предложить завершить/переназначить/оставить. Изменение суммы не должно задним числом превращать оценку в денежное поступление.

### 6.4 Appointment: запись и оказание услуги

**КОД:** статусы `created`, `confirmed`, `cancelled`, `rescheduled`, `completed`, `no_show`; терминальные — `cancelled/completed/no_show`. `apply_appointment_status` запрещает изменения архивных/терминальных записей и повтор того же статуса. Cancel и no-show требуют причины. [Services](../../apps/scheduling/services.py).

**КОД:** перенос меняет интервал/ресурс, сохраняет прежний рабочий status и пишет событие переноса. Наличие enum `rescheduled` не означает, что любой перенос должен выставлять его. Терминальные записи переносить нельзя. `restore` возвращает из архива, но не из `completed` в `created`.

**КОД:** [availability](../../apps/scheduling/availability.py) вычисляет конец по длительности услуги, использует timezone бизнеса, график ресурса с fallback к общему графику и проверяет пересечения. При отсутствии Resource проверка пересечений идёт по бизнесу в целом. Режим «без специалиста» поэтому нельзя обещать как неограниченную параллельную запись. Legacy `rescheduled` исключается из занятости — его миграционная/продуктовая трактовка входит в D-01.

**КОД:** при терминальном результате отменяются будущие appointment followups, а completion планирует post-service followup; отдельно создаётся follow-up задача: после отмены/no-show через 2 часа, после completion через день. Это существующий механизм, а не «отсутствующая автоматизация». Нужность и конфликт с пользовательскими правилами — D-04.

**ПРЕДЛОЖЕНИЕ:** новый визит после отмены/неявки — новая запись с происхождением, старый результат сохраняется. Ранний `completed/no_show`, исправление ошибочного результата и изменение длительности услуги после бронирования требуют отдельных правил D-05/D-06. На подтверждении всегда повторно проверять слот; показ свободного времени в селекторе не резервирует его навсегда.

### 6.5 Task: действие, а не продажа

**КОД:** `open → in_progress`; `open/in_progress → done` или `cancelled`; `done/cancelled → open` через reopen. Undo-cancel пытается восстановить прежний статус по audit, а не равен reopen. Snooze — время отложения, не отдельный статус; overdue — вычисляемый признак. Источник: [task services](../../apps/tasks/services.py).

**КОНТРАКТ:** cancel требует причины; update-details/assign/start/complete и другие действия — через соответствующий API. Recurrence не считать работающей только из-за исторического поля: [CRM plan](CRM_PRODUCTION_LAYER_PLAN.md) описывает отказ от её публичного использования до появления scheduler.

**ПРЕДЛОЖЕНИЕ:** задача без клиента допустима. Завершение подзадачи не завершает parent, а завершение задачи не закрывает Deal/Lead/Appointment. Для активной клиентской работы без ответственного или срока показывать риск/следующий шаг, не придумывая обязательность всех полей. Запрет циклов parent_task и согласованность CRM-связей проверять явно.

### 6.6 Inbox и сообщения

**КОД:** основной Inbox использует `BotConversation/BotMessage`; существуют также [legacy Conversation/Message](../../apps/conversations/models.py). Не создавать вторую историю и не суммировать обе модели как независимые обращения без доказанного mapping.

**КОНТРАКТ:** assign/take-over, read/unread, priority, close/reopen, qualification, link/create CRM и send/retry — отдельные действия [Inbox API](../api/API_ACTION_CONTRACT.md). `unread`, `handoff_required`, `bot_enabled`, `status` описывают разные состояния. Прочтение не равно ответу; назначение не равно решению; закрытие диалога не завершает сделку.

**КОД:** у сообщения есть `received`, `queued`, `delivering`, `retry_scheduled`, `sent`, `failed`. Не добавлять в интерфейс доказанную «доставку/прочтение клиентом», если provider receipt и соответствующая модель отсутствуют. `sent` не гарантирует, что клиент прочитал сообщение.

**ПРЕДЛОЖЕНИЕ:** новое валидное входящее после закрытия возвращает диалог в рабочую очередь и уведомляет текущего доступного ответственного; не создаёт новую заявку без нового намерения. Для архива/спама — отдельная политика D-02. У transport, состояния AI-агента и паузы AI в конкретном диалоге должны быть разные последствия.

### 6.7 Платежи клиента и подписка Zani

**КОНТРАКТ / WIP:** [manual journal](client-payments.md) предусматривает receipt, частичные поступления и partial/full refund, immutable ledger, разрешённую связь с клиентом/сделкой/записью и защиту повтора. UI и общий финальный gate в этом документе ещё не закрыты. Указанные там прошлые тесты не перезапускались в текущем этапе.

**КОНТРАКТ:** это фиксация денег вручную, без банковской транзакции, 1C-сверки, новых AI tools, изменения lifecycle сделки и финансовых KPI. Возврат записи в журнале не выполняет перевод денег.

**КОНТРАКТ:** SaaS billing имеет [entitlements](../billing/entitlements.md), модели подписки/лимитов и action API. Нельзя утверждать «billing вообще отсутствует», но наличие foundation не доказывает готовый платёжный провайдер, invoicing и коммерческий rollout. Отказ по лимиту должен объяснять ограничение и оставлять существующие CRM-данные доступными по действующей политике.

## 7. AI: помощь, разрешения и ответственность

**КОНТРАКТ:** AI использует реальные разрешённые источники, показывает отсутствие данных, не исполняет команды из входящих сообщений как административные инструкции и не подменяет domain services. Критические tools требуют связанного approved ApprovalRequest и повторной проверки underlying permission. Источники: [AI rules](../ai/AI_ASSISTANT_RULES.md), [модели](../../apps/ai_core/models.py), [auto pipeline](../../apps/conversations/auto_pipeline.py).

| Режим | Обнаруженный контракт | Чего он не разрешает |
| --- | --- | --- |
| `suggest_only` | Квалификация/предложение без создания CRM-сущностей | Скрытую запись в БД «для удобства» |
| `auto_lead_task` | Guarded создание client/lead/task | Произвольные terminal transitions, платежи, смену ролей |
| `draft_deal` | Дополнительно создание open/draft deal по policy | Автоматический won/lost; `draft` здесь не новый Deal.status |
| `appointment_explicit` | Запись после явного выбора клиентом предложенного доступного слота | Считать намерение/высокий confidence согласием на дату |
| Approval-gated tool | `pending → approved/rejected/expired`; после исполнения — `executed` | Одобрение через generic PATCH, другой payload, устаревшие права |

**РЕШЕНИЕ D-07:** общая формулировка «критические изменения только после подтверждения» и разрешённые auto-режимы должны иметь одну явную иерархию. Предлагается:

1. Для нового бизнеса — suggest-only до явного включения automation policy уполномоченным пользователем.
2. Ограниченная заранее включённая policy разрешает только перечисленные низкорисковые действия; каждое хранит origin, policy и результат.
3. Клиентское подтверждение слота разрешает конкретную запись, но не выдаёт клиенту CRM-права и не одобряет другие tools.
4. Переходы won/lost, массовые отправки, цены, платежи, права, destructive merge и иные критические действия — только по соответствующему явному разрешению; для gated tool — через существующий approval flow.
5. Перед выполнением проверить свежесть источников, доступность сущностей/слота и полномочия. Изменившееся предложение не исполнять по старому согласию.
6. При handoff/паузе прекратить автономные ответы и записи AI, но не терять валидные входящие из разрешённого transport. Последний пункт — D-02, не утверждение о текущем runtime.

**КОД:** рабочая версия [bot lifecycle](../../apps/bots/lifecycle.py) проверяет profile/channel/knowledge readiness, а [website boundary](../../apps/bots/views.py) требует активного канала и runtime-ready bot. Поэтому разделение AI pause/inbound сейчас нельзя объявлять подтверждённым во всех ветках. Не переносить результат исправления из другого worktree только по похожему названию задачи.

## 8. Автоматизации, фоновые операции и другие сущности

**КОНТРАКТ:** automation event сначала создаёт AutomationRun; поддерживаемые triggers/actions, idempotency, wait, checkpoint/retry, cancel и inline/queue режимы описаны в [runtime](../automation/automation-runtime.md). Список enum не равен списку поддерживаемых публичных действий. Будущее ожидание в inline-режиме само по себе не доказывает наличие работающего worker/beat.

**ПРЕДЛОЖЕНИЕ:** повтор после временной ошибки продолжает незавершённую работу, не повторяет уже подтверждённые effects. Cancel прекращает будущие шаги, не отменяет уже отправленные сообщения или проведённые бизнес-действия задним числом. Удалённая связь, отозванные права, отключённый модуль и неактивный исполнитель перепроверяются после ожидания. Системный follow-up и пользовательская automation rule должны иметь понятный приоритет и защиту дублирования, D-04.

## 9. Побочные эффекты: что меняется вместе, а что не меняется

**ПРЕДЛОЖЕНИЕ** для унификации; в колонке «найдено» перечислены только основания, а не результаты новых тестов.

| Действие | Связанные эффекты и история | Что не должно происходить автоматически | Найденное основание |
| --- | --- | --- | --- |
| Принято входящее | Сохранить один Message, обновить очередь/время, назначить/уведомить по policy; AI только если разрешён | Client/Lead/Deal/Appointment на каждое сообщение независимо от намерения | Inbox actions, auto pipeline |
| Создана заявка | Client relation, источник, activity/audit по контракту; lead_created trigger | Создание продажи и записи без цели/разрешения | Lead/automation services |
| Создана сделка из заявки | Связи и происхождение, единый client; актуализировать UI связанных карточек | Второй Client, удаление Lead, фиктивный Payment | create_deal_from_lead |
| Создана/перенесена запись | Проверка слота, interval, history, перепланирование разрешённых reminders | Изменение результата Deal, сохранение старого reminder как актуального | Scheduling services |
| Appointment completed/cancelled/no_show | История результата, отмена будущих reminders, существующий follow-up/task механизм; автоматизации только поддерживаемых событий | Повтор task при retry; automatic Payment; считать thank-you доставленным до отправки | Scheduling services; D-04 |
| Deal won/lost | Статус/этап/timestamps/history и соответствующие метрики | Каскадно завершить визиты, задачи, другие сделки клиента | Deal services |
| Task done/cancelled | История исполнителя/результата, пересчёт очереди | Автоматически закрыть parent или коммерческий процесс | Task services |
| Merge/archive/restore | Просмотр последствий, audit, согласованное обновление ссылок и UI | Неявный hard delete детей, повторная отправка/проведение старых effects | Client services, archive helper; D-03 |
| Payment/refund | Однократный ledger fact, audit, refresh журнала | Банковская операция, новый AI trigger или изменение won/completed | Manual journal contract |

Ошибки разделяются по границе фиксации: доменная транзакция не состоялась; основная запись сохранена, но доставка ожидает/не удалась; результат HTTP неизвестен после timeout. Для последнего сначала выяснить результат по существующей identity команды, затем разрешать безопасный retry. Нельзя советовать «создайте ещё раз» без проверки.

Не требуется создавать BusinessEvent на каждое локальное CRUD-действие ради унификации. Сначала использовать существующую activity taxonomy, automation triggers и зарегистрированные BusinessEvents; иначе один факт может повторно запустить несколько цепочек.

## 10. Analytics: смысл метрик и окончание процессов

**КОД:** [crm_metrics](../../apps/analytics/crm_metrics.py) и [reports](../../apps/analytics/reports.py) читают операционные сущности. Готовый отчёт не обязан ждать отдельного AnalyticsEvent на каждое действие. Отсутствие AnalyticsEvent само по себе не доказывает отсутствие записи в аналитике.

| Метрика/аспект | Фактическое основание | Целевой контракт — ПРЕДЛОЖЕНИЕ |
| --- | --- | --- |
| Заявки | Количество по source/status | Указать единицу «заявка», не «уникальный человек»; повторный контакт не равен новой заявке |
| Lead → Deal | Distinct lead_id среди видимых deals / видимые leads, с текущими фильтрами периода | Не удваивать conversion из-за нескольких deals; обозначить cohort и поведение сделки, созданной позже периода заявки |
| Won value | Сумма amount сделок с won | Назвать коммерческой суммой, не полученными деньгами |
| Completed / no-show rate | completed или no_show / все выбранные appointments | Подписать знаменатель; не выдавать за долю среди уже состоявшихся визитов, если включены будущие/отменённые |
| Revenue estimate / LTV | В reports используется текущая service.price_from для completed appointments | Считать оценкой, не ledger revenue; отсутствие цены не означает бесплатность. Исторический snapshot цены — D-06 |
| Unanswered | Открытые conversations с unread_count > 0 либо handoff_required | Это операционный proxy, не измеренный факт отсутствия человеческого ответа; одинаковая формула в очереди, dashboard и AI |
| Период | В crm_funnel Lead/Deal/Appointment/Task фильтруются по created_at, Conversation — updated_at; архивные исключены | Показывать фактический date basis. Не называть это автоматически «визиты/доход за дату оказания/оплаты» |
| Refund / cash | Payment journal не интегрирован в KPI в заявленном scope | Net cash = receipts − refunds только после отдельной согласованной реализации; не складывать cash, won amount и оценку визитов |
| Source ROI | `tracked_without_cost`, расхода на рекламу нет | Не представлять полноценной доходностью/прибылью |

**ПРЕДЛОЖЕНИЕ:** каждая метрика имеет источник, единицу, временное поле, timezone, валюту, фильтр архива, scope, знаменатель и правило обработки отсутствующих данных. Различать «0», «нет данных», «нет доступа», «модуль отключён» и «ошибка расчёта». Смена периода/роли не должна оставлять предыдущие чужие значения в UI.

Архив сегодня исключается из ряда операционных выборок, а reopen меняет текущее состояние. Это не неизменяемый исторический отчёт. Отдельную event-time/cohort/финансовую отчётность согласовать по D-06, не исправлять формулы молча при UI-аудите.

## 11. UI/UX-контракт действий

Это обязательные пользовательские критерии текущего аудита, **не утверждение, что они уже выполнены**. Использовать существующий design system, API-layer и i18n; не добавлять параллельные modal/select/toast реализации.

1. У каждого заполняемого поля — понятный label, обозначение обязательности и статичная `?` в строке label. Краткое «что это/зачем» доступно по hover, keyboard focus и tap; подсказка не является единственным носителем обязательного условия/ошибки. У управляющего переключателя/селектора объясняется его эффект.
2. Если prerequisite отсутствует, форма объясняет блокировку и предлагает разрешённое следующее действие. Не показывать бесконечную загрузку вместо пустого справочника. Сохранить введённое при создании prerequisite.
3. Состояния каждого CRUD/action flow: доступно → заполнение → client/server validation → pending → success либо безопасная ошибка. Для фоновой работы отдельно queued/running/partial/failed/cancelled, если они есть в реальном контракте.
4. Success — только после подтверждённого результата: «Клиент создан», «Изменения сохранены», «Запись отменена». «Поставлено в очередь» не равно «отправлено». Показывать последствие и доступную ссылку на результат.
5. Ошибка объясняет, что не получилось, безопасную причину и что можно сделать. Сохранять черновик, подсвечивать поле, не выводить raw provider text/stacktrace. `request_id` — дополнительная помощь для поддержки.
6. Повторная отправка заблокирована, пока команда выполняется. Retry доступен по серверному контракту; validation/permission/conflict не лечить бесконечным повтором. Timeout без определённого результата имеет отдельное состояние.
7. Close/cancel/backdrop/Escape и нативный file picker не теряют контекст; при несохранённых данных действует согласованный discard flow. Фокус возвращается на видимый trigger; overlay прокручивается и помещается на mobile.
8. Select/autocomplete: клавиатура, loading/empty/error, понятная выбранная сущность, защита от устаревшего async ответа. Недоступный исторический выбор объясняется, а не заменяется первым вариантом списка.
9. Причины loss/cancel/merge и необратимые последствия показаны до подтверждения. Restore из архива и reopen — разные действия и подписи.
10. Смена роли/tenant инвалидирует прежние данные/выборы. Ни tooltip, ни toast, ни count не раскрывают запрещённые сущности. Все пять ролей проверяются через backend и UI; профессия не заменяет роль.
11. RU/KK/EN, desktop/tablet/mobile, клавиатура и screen-reader labels входят в проверку. Toast не единственный способ узнать критическую ошибку; объявление результата доступно assistive technology.
12. Применять [ZR-001–ZR-009](../../actual_docs/DEFECT_KNOWLEDGE_BASE.md): стабильный ввод, отмена без потери контекста, проверка всех потребителей общего компонента, отсутствие технических утечек, корректный retry, overlay continuity и сохранение happy path.

1. Согласовать D-01–D-09 либо явно оставить отдельные решения открытыми. Это утверждение правил, а не разрешение реализовать всё разом.

4. Для подтверждённого отклонения выбирать один пакет: инвариант → service/action → permissions → effects → UI → целевые тесты. Один владелец и изолированный worktree для пересекающихся файлов.
5. Закрывать пакет только после доказательств разрешённого пути, отказа, tenant/scope isolation, связанных effects и доступного UI. Общий release gate — после интеграции; не переносить старое PASS на новую смесь WIP.
